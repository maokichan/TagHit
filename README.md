# TagHit

面向素材与收藏的本地内容标记与检索管理器。

## 为什么做 TagHit

创作和收藏会积累大量散落在本地各处的文件：素材库、截图、参考图、下载目录、项目产出……多年下来，"找"比"存"更花时间。文件夹层级只能表达一种分类，而内容天然是多维的——一张图既属于某个项目，又是某种风格，还服务于某个客户。

现有的工具各有短板：文件管理器只会目录；相册软件绑定单一媒体类型和它的云服务；数据库软件对媒体一无所知。**缺的是一个把"标注和检索"当作第一公民、数据完全留在本地的内容管理器。**

TagHit 的核心主张：

- **标签替代层级**：一个内容打多个标签，按任意标签组合切出视图——组织方式随你，而不是随目录树。
- **跨来源、跨目录**：内容在哪不重要，标签和条件说了算。同一个库，可以按项目、按类型、按任意组合切出视图。
- **数据归你**：本地索引、本地文件、单一数据库文件，没有云依赖，没有锁定。

## 它是什么样子

- **条目**：一个内容单元（一个文件，或一个无文件的作品锚点）。收录即扫描：自动记录文件事实（大小、修改时间、内容签名、图片尺寸），文件搬走了重新扫描即可恢复关联。
- **标签**：自由命名、声明式管理；打标、按标签过滤、逻辑组合检索。
- **作品**：把多个条目组织成一个有序整体（一张专辑的多支曲目、一个项目的多份文件），作品自身也可打标。
- **工作区**：内容视图——每个工作区索引一组目录（来源根）、声明自己可见的标签子集。同一库，不同视角：工作项目一个视角，私人收藏另一个。
- **预览**：图片、视频、音频、文本直接在库内预览；瀑布流/网格/列表多种浏览布局。

## 往哪里去

TagHit 正在朝**插件生态**演进（VS Code / Obsidian 式）：核心保持小而稳，布局、面板、检索增强、媒体能力由官方功能组件与三方插件经统一的贡献点机制提供——渲染层贡献面板与视图，主进程贡献计算能力（OCR、转码、自定义解析器），权限声明式管理。

## 当前状态

开发中：后端核心通过全量校准，桌面端（Electron）可真实运行——标签/检索/扫描/预览/多布局浏览/详情页工作台/插件生态机制 + 首个音频播放器插件（黑胶播放 + 歌词 + 全局播放）全链路可用。当前能力清单与进度见 `docs/CONTEXT.md` §三。

愿意现在试用的开发者：`npm install`（frontend 依赖）后 `npm run dev` 一键真机运行。

## 遇到问题（自诊断）

窗口黑屏、打不开、界面空白这类问题，应用自带**诊断快照**：

- 快照位置：`%APPDATA%/taghit/diagnostics.json`（随启动与加载事件自动更新；只含版本、路径与状态，**不含你的内容数据**）。
- 终端查看：`TagHit.exe --diagnose`——打印快照后退出，应用运行中也能用。
- 把快照文件交给能读它的助手/代理即可定位问题；首次界面加载失败时应用会弹窗指出快照位置。
